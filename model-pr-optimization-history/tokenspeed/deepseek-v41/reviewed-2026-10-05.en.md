### PR #1663 - Share the native decode schedule across layers in a forward

- Link: [#1663](https://github.com/lightseekorg/tokenspeed/pull/1663).
- Status/date: merged / 2026-09-20T12:56:25Z; +69/-6, 2 changed files.
- Diff scope read: all 149 diff lines at `3cfd377de881f4d222bf8be7c23f848cf9b9a75d`.
- Motivation: each attention layer previously created a fresh length-dependent
  decode schedule. Layers consuming the same SWA/global length tensors can
  share that producer within one forward, removing repeated metadata work.
- Key implementation: `DeepseekV41AttentionBackend._decode_schedule` caches
  the schedule by the identities of both length tensors and keeps those tensors
  alive. Refresh/rebind paths clear the cache; CUDA graph capture separately
  retains schedule objects. Reusing a schedule initialized in an earlier
  forward would omit the new length-dependent producer, so this is deliberately
  a per-forward cache, not persistent schedule memoization.
- Key code excerpt:

```diff
+        key = (id(swa_lens), id(global_lens))
+        entry = self._decode_schedules.get(key)
+        if entry is not None and entry[0] is swa_lens and entry[1] is global_lens:
+            return entry[2]
```

- Reviewed files: runtime
  `python/tokenspeed/runtime/layers/attention/backends/specific/deepseek_v41.py`;
  tests `test/runtime/test_deepseek_v41_cache.py`.
- Validation implications: the new test checks same-tensor reuse, a distinct
  SWA-only group, distinct equal-valued length tensors and invalidation on the
  next refresh. Preserve graph-capture lifetime and validate replay with changed
  lengths before applying this pattern elsewhere.

### PR #1685 - Fuse the FP8 index-query quantization into one kernel

- Link: [#1685](https://github.com/lightseekorg/tokenspeed/pull/1685).
- Status/date: merged / 2026-09-21T07:51:09Z; +92/-14, 3 changed files.
- Diff scope read: all 154 diff lines at `927bf1a844ad727b1be7c78248fb68ec6ee435f1`.
- Motivation: Hopper index scoring prepared queries through separate eager
  cast, reduction, clamp, division, quantization and weight-scale operations.
  DeepGEMM logits do not independently consume query scales, so the scale must
  remain folded into per-head weights when replacing that chain.
- Key implementation: `_quantize_index_queries_kernel` loads a token/head row,
  computes its FP32 amax scale, writes E4M3 queries and FP32 folded weights in
  one launch. `hopper_index_topk` calls this wrapper instead of the eager helper.
  Multiplying by `1/448`, using `tl.div_rn`, and disabling FP fusion preserve
  the reference's rounding points; a mathematically similar rewrite is not
  automatically equivalent for index selection.
- Key code excerpt:

```diff
+    scale = tl.maximum(tl.max(tl.abs(value), axis=0), 1.0e-6) * (1.0 / 448.0)
+    quantized = tl.minimum(tl.maximum(tl.div_rn(value, scale), -448.0), 448.0)
+    tl.store(QOut + row * O0 + head * O1 + d, quantized.to(tl.float8e4nv))
+    weight = tl.load(W + row * W0 + head * W1).to(tl.float32)
+    tl.store(WOut + row * F0 + head * F1, weight * scale)
```

- Reviewed files: runtime `tokenspeed-kernel/python/tokenspeed_kernel/ops/attention/dsv41/deep_gemm.py`
  and `triton.py` in the same directory; tests
  `tokenspeed-kernel/test/ops/test_attention_dsv41.py`.
- Validation implications: the added test compares E4M3 byte payloads and
  folded weights with zero tolerance for contiguous and strided queries.
  Retain these checks and exercise actual index top-k, including padded/empty
  rows. A removed launch does not by itself establish serving latency savings.

### PR #1794 - Stop recompiling compressor metadata on every prefill chunk

- Link: [#1794](https://github.com/lightseekorg/tokenspeed/pull/1794).
- Status/date: merged / 2026-09-25T13:09:10Z; +48/-4, 2 changed files.
- Diff scope read: all 74 diff lines at `6cb384bef40eb095fdf4d591eceb83b832efb13e`.
- Motivation: the table dimensions and strides grow during chunked prefill.
  Making them `tl.constexpr` creates a new JIT specialization for new geometry
  on the serving thread, even though the kernel can load them at runtime.
- Key implementation: `_compressor_metadata` receives TR/TC/TS0/TS1 as runtime
  scalars. Stable page/block geometry remains compile-time. This removes one
  source of recompilation; runtime integers can still specialize by alignment.
- Key code excerpt:

```diff
-    TR: tl.constexpr,
-    TC: tl.constexpr,
-    TS0: tl.constexpr,
-    TS1: tl.constexpr,
+    TR,
+    TC,
+    TS0,
+    TS1,
```

- Reviewed files: runtime `tokenspeed-kernel/python/tokenspeed_kernel/ops/attention/dsv41/triton.py`;
  tests `tokenspeed-kernel/test/ops/test_attention_dsv41.py`.
- Validation implications: the test warms both integer specialization classes,
  sweeps rows/table widths, checks exact metadata and asserts no new compile.
  Cold-start compile timing and warmed serving latency answer different questions.

### PR #1814 - Stop recompiling compressor pooling for every prefill length

- Link: [#1814](https://github.com/lightseekorg/tokenspeed/pull/1814).
- Status/date: merged / 2026-09-27T03:45:26Z; +75/-8, 4 changed files.
- Diff scope read: all 157 diff lines at `66d5f3b6e833bee52f20d8b45c11804072be9b72`.
- Motivation: `_compressor_pool` specialized on the forward's token count,
  creating new binaries for varying prefill lengths. The fix applies the same
  runtime-scalar principle as #1794 to pooling, and makes the no-compile test
  reusable for future kernels.
- Key implementation: N becomes a runtime argument; `assert_no_triton_compile`
  wraps `_do_compile` and rejects compilation after warmup. The PR also updates
  upstream contributor guidance and uses the helper for the metadata test.
- Key code excerpt:

```diff
-    N: tl.constexpr,
+    N,
+    with assert_no_triton_compile(implementation._compressor_pool):
+        for count in (48, 97, 130, 1483, 4096):
+            run(count)
```

- Reviewed files: runtime `tokenspeed-kernel/python/tokenspeed_kernel/ops/attention/dsv41/triton.py`;
  tests `tokenspeed-kernel/test/ops/test_attention_dsv41.py`,
  `tokenspeed-kernel/test/utils.py`; contributor guidance `AGENTS.md`.
- Validation implications: warm aligned and unaligned counts, then vary row
  counts while comparing pooled output with the reference. Recheck mask/tail
  semantics and graph replay. The upstream guidance's latency example is not
  a measurement performed by this refresh.
